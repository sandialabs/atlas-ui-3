# FastMCP 4 and MCP 2026-07-28

Date: 2026-11-25 (issue #905)

Atlas moved from `fastmcp` 3.x to 4.x. FastMCP 4 implements MCP protocol revision `2026-07-28`, which changes how a server asks the user for input and how background tasks work. This note records what changed in Atlas and why.

## What the protocol changed

- **No server-initiated requests (SEP-2322, SEP-2575).** A 2026-07-28 connection is a stateless request/response envelope with no back-channel. A tool can no longer send `elicitation/create` and wait. It returns an `InputRequiredResult` listing the input it needs, and the client retries the call with `inputResponses` and the echoed `requestState`. `ctx.elicit()` raises on such a connection.
- **Tasks are an extension (SEP-2663).** The server decides whether a call runs as a task and answers `tools/call` with a task handle. The client polls `tasks/get`. `Client.call_tool(task=True)`, `ToolTask.on_status_change` and the per-tool `execution.taskSupport` metadata are gone.
- **No connection-scoped session state.** Each request is its own connection, so `ctx.get_state` / `ctx.set_state` no longer carries data between tool calls. FastMCP 4 offers explicit sessions (`SessionProvider`, `get_session`) instead.
- **The Python SDK renamed its model fields to snake_case** (`tool.input_schema`, `content.mime_type`, `params.requested_schema`).

FastMCP's `Client` defaults to `mode="auto"`: it probes `server/discover` and falls back to the `initialize` handshake for a server that does not speak 2026-07-28. Atlas keeps that default, so FastMCP 3 servers keep working unchanged, including `ctx.elicit()` over the back-channel.

## Elicitation routing

The wire format between the backend and the browser is unchanged apart from two added fields on `elicitation_request` (`mode`, and `url` for URL requests). What changed is how the backend decides which tool call a request belongs to.

FastMCP calls Atlas's `elicitation_handler` in both eras, but from different places:

| Era | Who calls the handler | Task it runs in |
|-----|-----------------------|-----------------|
| 2026-07-28 | The multi round-trip driver inside `Client.call_tool` | A child of the task that made the call |
| Handshake | The session's receive loop, on an `elicitation/create` request | The receive loop's task |

On a 2026-07-28 session the handler therefore inherits the caller's context. `_use_elicitation_context` now sets a contextvar as well as the `(server_name, tool_call_id)` dictionary entry, and `_resolve_routing` uses the contextvar entry when the session is modern, provided it is still the registered entry for that call. Request `_meta` from the server is ignored there, so a server cannot redirect a prompt to another call, and a call with no entry prompts nobody. This is strictly stronger than the previous single-match scan: two users calling the same shared STDIO server at the same time now each get their own prompt.

On a handshake-era session the contextvar is not trusted. The receive loop was started by whichever call opened the session, so its context would name the wrong call. The protocol carries no reference from an `elicitation/create` request to the `tools/call` that caused it, so a prompt is only delivered when the answer is unambiguous:

- exactly one call is live on that server, or
- several are live and the request meta names one of them by the `tool_call_id` Atlas sent with the call.

Everything else is cancelled. In particular a meta id that matches no live call is not redirected to whichever call happens to be alone on the server (before this change it fell through to the single-match scan).

Tool call ids come from the model provider and are not guaranteed unique across users. If two live calls to one server share an id, the routing key is marked ambiguous until both have finished and neither can be prompted, in either era.

The ownership check on the response (`ElicitationRequest.user_email`) is unchanged and applies to both eras.

## Background tasks

`MCPToolManager` no longer chooses task mode. It makes an ordinary `call_tool`; FastMCP's tasks client extension polls a tasked call to completion. Atlas substitutes `AtlasTasksClientExtension` for the built-in one (same extension identifier, which FastMCP documents as the override mechanism). It wraps the stock resolver and adds:

- a `TaskCallTracker`, so `call_tool` knows the call was tasked and can send `tool_task_started` after `MCP_TASK_TIMEOUT` seconds and `tool_task_completed` at the end. The frontend marks the open tool row ("BACKGROUND TASK", "running in the background") between the two. The delay is capped at half of `MCP_CALL_TIMEOUT`, so a deployment whose call timeout is shorter than the task threshold still sees the announcement;
- a `tasks/cancel` request when the waiting call is cancelled or times out. Without it, stopping a run left the task executing on the server.

Removed with the old mechanism: the per-tool task-forbidden cache and its discovery seeding, `_supports_tasks`, and the `tool_task_progress` event (the new protocol has no status notifications; the frontend never consumed it).

Tasks exist only on 2026-07-28 connections. A FastMCP 3 server's optional-mode task tools run inline; a tool declared `mode="required"` on a FastMCP 3 server cannot be called until that server is upgraded.

## Frontend

- Pending elicitations are a queue. A single round trip may carry several questions, and they are dispatched together, so replacing the dialog on each `elicitation_request` would strand all but the last.
- The form understands the schema shapes the current specification allows: titled choices (`oneOf`/`anyOf` of `const` + `title`, and `enumNames`), multi-select arrays, `title`, numeric ranges, string formats and lengths.
- URL-mode requests are shown with the full address and an explicit **Open link** action. Non-`http(s)` URLs are declined by the backend and never rendered as a link by the frontend. The FastMCP client advertises URL support unconditionally, so not handling it was not an option.

## Bundled servers

- `elicitation_demo` uses `atlas/mcp_shared/user_input.py`, a small helper that returns `InputRequiredResult` on a 2026-07-28 connection and falls back to `ctx.elicit()` otherwise. Answers from earlier rounds travel in `request_state`, so nothing is stored on the server.
- `task_demo` registers `TasksExtension`.
- `session_state_demo` uses explicit sessions (`create_session` + a `session_id` argument).
- `image_demo` imports `ToolResult` from its new location.

## Horizontal scaling

Nothing here adds replica-local state. The pending-elicitation registry was already in-process (the waiting tool call and its MCP connection live on one replica, and the response is delivered to the replica that owns the run); that is unchanged. Multi round-trip elicitation is, if anything, friendlier to multiple MCP server replicas, because the server holds no state between rounds.

## Verification

- `atlas/tests/test_mcp_elicitation_round_trip.py` drives the real demo servers over STDIO in both eras, including two concurrent users on one shared client and task cancellation.
- `test/pr-validation/fixtures/pr1254/manager_e2e.py` drives `MCPToolManager` end to end (discovery, elicitation, tasks, images, progress, prompts).
- Mock-based tests did not catch the snake_case rename, because the stand-in objects carried the old attribute names. They were updated to the SDK's real field names.
